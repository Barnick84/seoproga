# Детальный план рефакторинга и улучшений `seo-auto-cluster` (27 задач)

Данный документ содержит максимально подробный, пошаговый план исправления 27 выявленных архитектурных проблем, багов и недочетов в проекте `seo-auto-cluster`. План разбит на фазы по приоритетам.

---

## Фаза 1: Критические ошибки (P0) — Немедленное исправление

*Эти проблемы блокируют корректную работу основного функционала или приводят к потере данных.*

### 1. Отсутствие `conn.commit()` при сохранении SEO-анализа

* **Файл:** `scripts/run_seo_analysis.py` (строка ~248)
* **Проблема:** После успешного выполнения анализа и выполнения `INSERT INTO cluster_analysis ... ON DUPLICATE KEY UPDATE` нет вызова `conn.commit()`. Из-за `autocommit=False` данные теряются.
* **Решение:**
  Добавить `conn.commit()` сразу после `cur.execute(...)` и перед `print(json.dumps(...))`.

### 2. Использование кортежа как словаря (`dictionary=True`)

* **Файл:** `scripts/run_clustering.py` (строка ~40)
* **Проблема:** Создается обычный курсор `cur = conn.cursor()`, но данные извлекаются как из словаря: `cid = row["clustered"]`. При первой же попытке повторной кластеризации скрипт падает с `KeyError`.
* **Решение:**
  Заменить `cur = conn.cursor()` на `cur = conn.cursor(dictionary=True)` или `cur = conn.cursor(named_tuple=True)`, либо обращаться по индексам `row[0]`, `row[1]`. (Предпочтительно `dictionary=True`).

### 3. Несовместимость SQL-синтаксиса (`ON DUPLICATE KEY UPDATE`)

* **Файлы:** `api/routers/cluster.py` (6 мест: строки 161, 194, 334, 368, 400, 428)
* **Проблема:** Проект позиционирует поддержку нескольких СУБД (PostgreSQL, MySQL, SQLite), но жестко завязан на MySQL-специфичный `ON DUPLICATE KEY UPDATE`.
* **Решение:**
  Заменить `ON DUPLICATE KEY UPDATE` на `SELECT` + `UPDATE`/`INSERT` (как это сделано в `cache.py`), либо написать хелпер в `utils/db.py`, который генерирует корректный `upsert` запрос в зависимости от `Config.DB_TYPE` (`ON CONFLICT DO UPDATE` для PG).

### 4. Hardcoded `user_id = 1` в CLI и Workflow

* **Файлы:** `services/seo_workflow.py` (строка 106), `scripts/run_seo_analysis.py` (строка 157)
* **Проблема:** Если скрипты или workflow вызываются без явного указания `user_id`, они жестко привязываются к `user_id = 1`. Это критично для многопользовательской SaaS системы — данные перемешиваются.
* **Решение:**
  Убрать дефолтные значения `user_id=1`. Сделать параметр обязательным, выбрасывать ошибку (`raise ValueError` / `print(json.dumps({'error': ...}))`), если он не передан.

### 5. `pymorphy3.MorphAnalyzer()` загружается при импорте

* **Файл:** `services/custom_analyzer.py` (строка 19)
* **Проблема:** Глобальная инициализация `morph = pymorphy3.MorphAnalyzer()`. При каждом импорте модуля грузится 200MB словарь, что блокирует старт FastAPI и тратит память.
* **Решение:**
  Использовать ленивую инициализацию (Singleton):

  ```python
  _morph = None
  def get_morph():
      global _morph
      if _morph is None:
          import pymorphy3
          _morph = pymorphy3.MorphAnalyzer()
      return _morph
  ```

### 6. Мусорные данные в `STOP_WORDS`

* **Файл:** `services/custom_analyzer.py` (строки 21-253)
* **Проблема:** В множестве (`set`) находится более 80 дублей слов (например, "они" 3 раза).
* **Решение:**
  Очистить множество, оставив только уникальные слова.

### 7. Несовпадение `InvId` и `order_id` в webhook биллинга

* **Файл:** `api/routers/billing.py` (строка 139)
* **Проблема:** В `payment_successful` используется `order_id = InvId`. Нужно удостовериться, что Cardlink передает сгенерированный нами `ORDER_{timestamp}_{user_id}` именно в параметре `InvId`. Если нет — транзакции не будут засчитываться.
* **Решение:**
  Проверить документацию Cardlink или добавить детальное логгирование входящего payload в webhook.

## Фаза 2: Существенные проблемы (P1) — Стабильность и безопасность

### 8. Отсутствие таймаутов у `subprocess`

* **Файлы:** `api/routers/positions.py` (строки 80, 246), `api/routers/analysis.py` (строка 222)
* **Проблема:** При использовании `await proc.communicate()` или чтении `stdout` в цикле нет таймаутов. Если дочерний скрипт зависает, FastAPI worker висит бесконечно.
* **Решение:**
  Обернуть вызовы в `asyncio.wait_for(..., timeout=300)`. При `TimeoutError` вызывать `proc.kill()` и возвращать ошибку 504.

### 9. Уязвимость DoS через `limit` без ограничений

* **Файл:** `api/routers/positions.py` (строка 101)
* **Проблема:** `limit: int = 500` не валидируется сверху. `?limit=10000000` может привести к OOM (Out of Memory).
* **Решение:**
  Использовать Pydantic `Query`: `limit: int = Query(default=500, ge=1, le=10000)`.

### 10. Boilerplate код подключения к БД (Дублирование ~15 раз)

* **Файлы:** `api/routers/cluster.py`, `positions.py`, `analysis.py`
* **Проблема:** Каждый endpoint повторяет `conn = Config.get_conn()`, `try...finally: cur.close(); conn.close()`.
* **Решение:**
  Создать контекстный менеджер в `utils/db.py`:

  ```python
  from contextlib import contextmanager
  from config import Config
  
  @contextmanager
  def get_db_cursor(dictionary=True, commit=False):
      conn = Config.get_conn()
      try:
          cur = conn.cursor(dictionary=dictionary)
          yield conn, cur
          if commit: conn.commit()
      except Exception:
          conn.rollback()
          raise
      finally:
          cur.close()
          conn.close()
  ```

### 11. Отсутствие валидации `domain` (SSRF / Утечка данных)

* **Файлы:** Все роутеры API.
* **Проблема:** Пользователь передает `domain` строкой. Нет проверки, что этот домен действительно принадлежит этому пользователю (присутствует в таблице `sites` с его `user_id`).
* **Решение:**
  Добавить зависимость в FastAPI (Dependency), которая валидирует домен по таблице `sites`.

### 13. Запуск Python скриптов через `subprocess` в HTTP-хендлерах

* **Файлы:** `api/routers/cluster.py` (5 мест)
* **Проблема:** Запуск скриптов с парсингом JSON через регулярки из stdout — это очень хрупко и медленно.
* **Решение:**
  Так как теперь всё на Python, нужно импортировать логику напрямую из `scripts/` и выполнять через `await asyncio.to_thread(func, args)`. (Это потребует рефакторинга скриптов, чтобы они возвращали dict, а не делали `print(json.dumps)`).

### 14. Гонка данных (Race Condition) в `worker.py`

* **Файл:** `services/worker.py` (строка 59)
* **Проблема:** `active_processes = []` — глобальный список. Добавление и удаление процессов не потокобезопасно.
* **Решение:**
  Использовать `threading.Lock` при манипуляциях с `active_processes`.

### 15. Синхронные HTTP запросы в `ThreadPoolExecutor`

* **Файл:** `services/custom_analyzer.py` (строка 615)
* **Проблема:** `requests.get` внутри тредпула тратит системные ресурсы.
* **Решение:**
  Переписать на `aiohttp` и использовать `asyncio.gather` для параллельных I/O запросов (до 10 конкурентов).

### 16. Скрытие ошибок (`bare except`)

* **Файл:** `scripts/generate_seo_plan.py` (строки 121, 142)
* **Проблема:** `except: pass` глушит все исключения, включая системные прерывания.
* **Решение:**
  Заменить на `except Exception as e: logger.warning(e)`.

## Фаза 3: Технический долг (P2)

### 17. Огромная нехватка тестов (Покрытие ~1%)

* **Директория:** `tests/`
* **Проблема:** Тестируются только 2 функции из `clustering.py`.
* **Решение:**
  Добавить unit-тесты для `SERPCache`, `CustomAnalyzer`, валидации биллинга (`check_and_deduct_balance`) и интеграционные тесты для API через `TestClient`.

### 18. N+1 Query в роутере позиций

* **Файл:** `api/routers/positions.py` (строки 27-47)
* **Проблема:** Делается запрос к `cluster_mappings`, а затем отдельный запрос к `cluster_names`.
* **Решение:**
  Объединить в один запрос через `LEFT JOIN`.

### 19. Бесконтрольное формирование N-грамм

* **Файл:** `services/custom_analyzer.py` (строка 382)
* **Проблема:** `generate_ngrams` возвращает все n-граммы, даже те, что встречаются 1 раз.
* **Решение:**
  Отфильтровать: `return {k: v for k, v in Counter(ngrams).items() if v >= 2}`.

### 20. Некорректный подсчет "тошноты"

* **Файл:** `services/custom_analyzer.py` (строка 362)
* **Проблема:** Текущая формула (самое частое слово / все слова) — это "академическая", а не "классическая" тошнота.
* **Решение:**
  Исправить формулу или переименовать поле в `academic_stuffing`, чтобы не вводить SEO-специалистов в заблуждение.

### 21. `get_system_settings` скрывает ошибки БД

* **Файл:** `api/routers/analysis.py` (строка 78)
* **Проблема:** При падении БД или проблемах связи функция молча возвращает тариф 0.10, вместо того чтобы выбросить 500 ошибку. Пользователи могут парсить задешево при сбоях БД.
* **Решение:**
  Логгировать ошибку и, возможно, возвращать "безопасные" максимальные тарифы, либо падать.

### 22. Отсутствие индекса для истории позиций

* **Файл:** `SQL Schema` (Таблица `query_history`)
* **Проблема:** Запросы к истории идут по полям `(user_id, site_url, engine, device)`. Без составного индекса таблица будет тормозить при росте.
* **Решение:**
  Добавить `CREATE INDEX idx_query_history_lookup ON query_history (user_id, site_url, engine, device);`.

## Фаза 4: Архитектурные улучшения (P3)

### 23. N×UPDATE в цикле вместо Batch/Executemany

* **Файл:** `scripts/run_clustering.py` (строка 118)
* **Проблема:** При сохранении кластеров делается отдельный `UPDATE` для каждого ключа. 5000 ключей = 5000 запросов к БД.
* **Решение:**
  Использовать `cur.executemany(...)` с подготовленным списком кортежей.

### 25. Нет Connection Pool (✅ Исправлено)

* **Файл:** `config.py`
* **Проблема:** На каждый HTTP запрос открывается новое TCP соединение с MySQL. Это "убьет" базу при нагрузке 50+ RPS.
* **Решение:**
  Интегрирован `DBUtils.PooledDB` (синхронный пул потоков) для MySQL и PostgreSQL в `config.py`. Это позволяет избежать дорогого асинхронного рефакторинга всех роутеров, но при этом эффективно переиспользует соединения и защищает БД (maxconnections=20, blocking=True).

### 26. `SELECT *` в биллинге

* **Файл:** `api/routers/billing.py` (строки 31, 37)
* **Проблема:** Запрос всех столбцов. Схема может измениться (добавятся технические поля).
* **Решение:**
  Указать явные столбцы: `SELECT id, amount, description, created_at, type FROM ...`.

### 27. Отсутствие Auto-Retry для Background Tasks

* **Файл:** `services/worker.py`
* **Проблема:** Задачи, упавшие из-за случайного сетевого сбоя XMLRiver, остаются в `failed` навсегда.
* **Решение:**
  Добавить поле `retry_count` в таблицу `tasks` и логику перезапуска (максимум 3 раза).
